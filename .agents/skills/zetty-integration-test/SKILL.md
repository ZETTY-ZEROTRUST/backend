# $zetty-integration-test

사용자가 지정한 ZETTY 로컬 통합 테스트를 실행합니다. 테스트 케이스·선택자·이미지 태그는 각각 의미가 다르므로 요청과 실제 runner 옵션에서 확인합니다. 임의의 branch→tag 규칙을 만들지 않습니다.

## 이 파일의 역할 — 오케스트레이션만

**시나리오 정의는 이 파일에 두지 않습니다.** 실행 절차·검증 명령·기대 응답은 전부
`backend/README.md`, `uba-analyzer/README.md`, `attack-simulation/README.md`, `zero-trust-architecture/compose/README.md`의 실제 실행 절차가 소유하며, 이 command는 "어떤 케이스를 고르고,
어떤 순서로 태우고, 어떻게 보고할지"만 규정합니다.

시나리오·기대값은 실제 owner 문서와 테스트 코드에서 읽습니다. endpoint·payload·예상 결과를 이 스킬에 복제하지 않습니다. Markdown 케이스 문서가 없어도 기존 테스트 함수·runner가 검증 범위와 기대값을 정의할 수 있습니다.

경로는 ZETTY 워크스페이스 기준입니다. 개별 레포 clone에서는 현재 레포의 README와 테스트 코드를 먼저 읽고, 없는 형제 레포가 필요한 검증만 미실행으로 보고합니다.

## 실행 순서

### Step 0 — 테스트 케이스 선택

사용자가 지정한 케이스·명령·실패 결과가 있으면 그것을 선택합니다. 없으면 대상 변경과 owner README에서 해당 테스트를 찾습니다.

- backend: 실제 존재하는 변경 모듈 테스트. PostgreSQL SQL·잠금·중복 계약은 승인된 전용 PostgreSQL에서 검증한다.
- uba-analyzer: 실제 구현된 수신·멱등성·집계·분석·보고서 테스트와 선택자. README만 있으면 실행 미구현으로 보고한다.
- attack-simulation: `README.md`의 현재 두 시나리오와 앞으로 구현될 실제 runner. 삭제된 `scenarios/v2/`·`load/`를 실행 경로로 안내하지 않는다. 정의만 있고 runner가 없으면 실행 미구현으로 보고한다.
- Compose: `compose/README.md`와 local-runtime-design.md를 대조한다. 구형 Compose는 제거했으며 새 구성이 없으면 해당 검증은 SKIP이다.

서로 다른 실행 대상 중 선택이 필요한 경우에만 사용 가능한 질문 도구 또는 일반 질문으로 필요한 범위를 확인합니다. 이미 지정된 케이스를 재확인하지 않습니다.

### Step 1 — 시나리오 범위 선택

요청의 전체/일부 범위와 실제 테스트 의존 관계를 확인합니다. 실행 가능한 선행 setup이 명확하고 승인된 범위에 포함되면 함께 실행하고 알립니다. 의존 관계가 불명확하다는 이유로 일부 요청을 전체 실행으로 넓히지 않습니다. 해결할 수 없는 의존 부분만 질문 또는 SKIP으로 남깁니다.

local target allowlist·모의 계정·요청량·기간·timeout·종료 조건을 실제 runner와 맞춥니다. 선택 완료 후 케이스·대상·예상 정리 범위를 한 줄로 알립니다.

### Step 2 — Setup 실행

실제 owner의 전제 조건과 명령을 읽고, 승인된 로컬 테스트에 필요한 의존성·이미지·일회용 서비스를 준비합니다. 명령을 다른 레포에서 실행하거나 기존 stack을 테스트용으로 초기화하지 않습니다. 이미지 태그는 명시된 override 또는 실제 runner의 규칙만 사용합니다.

목표 DB는 PostgreSQL이며 현재 코드의 전환 완료 여부는 실제 파일로 확인합니다. 승인된 PostgreSQL 검증에서 schema 초기화는 새 테스트 DB에만 적용합니다. 기존 DB의 데이터 이동·스키마 전환은 해당 검증 절차를 따르며 초기화 SQL을 무조건 재실행하지 않습니다.

### Step 3 — 시나리오 실행

Step 1에서 확정한 시나리오를 케이스 파일의 정의대로 실행합니다. 각 시나리오의 PASS/FAIL은
**케이스 파일이 명시한 기대값**으로만 판정합니다(이 command가 기대 코드를 따로 정하지 않습니다).

### Step 4 — Teardown

runner의 cleanup/trap 또는 케이스의 Teardown을 확인해 자신이 만든 일회용 컨테이너·네트워크·임시 파일만 정리합니다. 기존 서비스의 기동 상태와 데이터 볼륨은 유지합니다.

### Step 5 — 결과 보고

케이스 파일에 `보고 양식`이 있으면 그 양식을 그대로 씁니다. 없으면 아래 기본 양식을 사용합니다.

```
[run-integration-test] 완료

## 케이스
<케이스 제목> (<파일 경로>)

## 이미지
<해당 앱의 로컬 검증 이미지>

## 결과 요약
| 번호 | 테스트 | 결과 | HTTP |
|------|--------|------|------|
| ...  | ...    | ...  | ...  |
(실제 실행한 시나리오만 행으로 넣습니다 — 스킵된 것은 결과란에 SKIP과 사유)

PASS: N · FAIL: N · SKIP: N

## FAIL 상세 (있을 때만)
- <번호>: <테스트명> — 기대 <기대값>, 실제 <실제값>
  응답: <바디 요약>

## 비고
- 컨테이너: <이름> (종료·삭제 여부)
- 임시 파일: 정리 여부
```

FAIL이 있으면 `docker logs <컨테이너>`의 관련 구간에서 비밀·토큰·쿠키·업무 본문을 제거한 진단을 첨부하고, 아래 블록을 생성합니다:

```
## 수정 요청 ← 이 블록을 $zetty-fix-test-failure 에 그대로 전달

케이스: <케이스 파일 경로>
실패 시나리오:
- <번호>: <테스트명> — 기대 <기대값>, 실제 <실제값>
  응답: <바디 요약>
  컨테이너 로그: <관련 ERROR 줄>

이미지: <해당 앱의 로컬 검증 이미지>
브랜치: <현재 브랜치>
```

## 중단 조건

- owner 문서와 실제 코드에서 검증 정의를 찾을 수 없음 → 해당 검증 미실행과 필요한 정의를 보고.
- 승인된 준비로 해결할 수 없는 전제 조건 미충족 → 해당 범위만 SKIP, 가능한 독립 검증 계속.
- 기동 timeout → 해당 서비스 진단을 민감값 제거 후 보고하고 자신이 만든 자원 정리.
- 선행 시나리오 실패 → 실제 의존 규칙에 따라 후속만 SKIP. 독립 케이스는 계속.
- 수정 요청이 있으면 설치된 `$zetty-fix-test-failure`를 적용. 스킬이 없으면 같은 원인 분석→제한된 수정/검토→실패 케이스 재검증 절차를 주 세션에서 수행하고 독립 검토 여부를 보고.
## ZETTY 실행 제한
요청에 케이스·범위가 명시되면 다시 묻지 않는다. 불명확할 때만 필요한 범위를 확인한다. local allowlist·모의 계정·요청 수·기간·종료 조건을 확인한다. 자신이 만든 일회용 자원만 정리한다. JWT/쿠키/비밀번호/키/업무 본문은 실패 보고에서 제거한다.

## 참고 코드와 모니터링 적용

backend/docs/reference-adoption.md R24와 monitoring-design.md의 해당 인수 기준을 사용한다. 실제 HTTP 쿠키·CSRF·세션 회수·객체 인가 및 필터 순서/중복, 실제 PG의 원자성/거부 rollback/권한, 요청 ID·시각 연결을 검사한다. 단일 worker의 중단/재시작·포화·늦은 완료·ACK 유실, UBA/Jev 중단 중 수신/기록과 복구 후 대기 해소를 구분한다. required DB/Redis readiness, 공개 health 상세 비노출, idle/unknown/no-history를 검사한다. unit/integration/실제 모델 평가를 별도로 보고한다. 실제 task/환경과 승인 범위가 없으면 해당 항목만 SKIP하며 문서 요청으로 서비스를 실행하지 않는다.

## 구조와 작업 범위

[현재 선택한 구조와 작업 경계](../../references/system-design.md)를 먼저 읽는다. 목표는 서버 세션을 사용하는 단일 backend(네 Gradle 모듈, 실행 앱 하나)와 uba-analyzer, PostgreSQL이다. 실제 구현은 단계별로 확인한다. 기존 Auth/API/BFF·MySQL 코드를 목표 구조가 구현됐다는 증거로 쓰거나, 기존 JWT 기능을 반드시 보존할 목표로 취급하지 않는다.

사용자와 변경 이유·흐름·대상 파일·검증 방법을 먼저 정하고 승인한 단계만 구현한다. 같은 범위의 승인을 반복 요청하지 않는다. 설계·문서·에이전트 구성 요청은 실행 코드·SQL·의존성·Compose·데이터 변경이나 서비스/공격/유료 API 실행 권한이 아니다. trust-chain-server 원본은 읽기 전용이다.

경로는 워크스페이스 기준이다. 개별 clone에서는 자기 README와 실제 파일을 먼저 확인하고 없는 형제 레포가 필요한 검증만 미실행으로 남긴다. 삭제된 log-pipeline 런타임·계약·테스트를 복원하지 않는다. Java 전달 작업은 backend, Python 수신·집계·Jev·보고서는 uba-analyzer가 소유한다.
