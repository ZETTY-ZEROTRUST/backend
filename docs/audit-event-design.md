# 감사 기록과 UBA 전달 설계

2026-11-27 설계안. 구현된 JSON Schema나 실행 가능한 전송 API를 뜻하지 않는다. 기존 이벤트 계약을 세션 구조에 그대로 적용하지 않는다.

## 저장 경계

- 일반 운영 로그: SLF4J → Logback → 마운트된 회전 파일.
- `zetty_backend.audit_events`: 로그인·업무 조회의 관측 사실.
- `zetty_backend.audit_delivery`: 전송 대기·재시도·수신 확인 상태.
- `zetty_uba`: 수신 이벤트·분석 작업·보고서. UBA는 업무 DB를 직접 읽지 않는다.

로컬 PostgreSQL 인스턴스 하나에 앱별 논리 DB와 접속 계정을 분리한다. 물리 장애·DB 관리자 권한까지 격리하는 구조는 아니다.

## 이벤트 필드 초안

| 필드 | 의미 |
|---|---|
| event_id / schema_version | 고유 식별자·계약 버전 |
| occurred_at | 관측 발생 시각, PostgreSQL TIMESTAMPTZ |
| recorded_at / received_at | backend 영속 기록 시각 / UBA 수신 기록 시각. 발생 시각을 덮어쓰지 않음 |
| actor_key / audit_session_key / key_version | 검증된 가명 주체·감사 세션·가명화 버전 |
| request_id | 요청 상관관계. 인증 주체의 증거로 사용하지 않음 |
| event_type / action | 로그인·주문 조회 등 사건과 행위 |
| resource_key | 가명 대상 식별자 |
| outcome / reason | 성공·거부·실패와 서버가 확인한 사유 |
| details | 이벤트별 추가 맥락, JSONB |

received_at은 UBA가 최초 수신 시 별도로 저장하는 메타데이터이며 producer payload나 동일 event_id의 내용 비교 대상에 포함하지 않는다. 같은 이벤트의 중복 수신으로 최초 수신 시각을 덮어쓰지 않는다. 필요하면 재수신 시도 시각을 별도 운영 기록으로 남긴다.

자주 조회하는 공통 값은 컬럼에 두고 추가 맥락만 JSONB에 저장한다. 필요한 조회에 맞춰 인덱스를 추가하며 GIN·기간 파티셔닝을 처음부터 모두 도입하지 않는다. JSONB는 원문 JSON 바이트 보존을 보장하는 형식이 아니다.

실제 쿠키·비밀번호·토큰·개인정보 응답 본문은 저장·전달하지 않는다. 로그인 실패의 입력 계정을 검증된 actor로 만들지 않는다. IP를 넣는 경우 신뢰 프록시 경계를 먼저 정하고 User-Agent는 조작 가능한 참고 정보로 취급한다.

request_id는 요청 진입에서 한 번 생성·확정해 요청 속성 및 일반 로그 컨텍스트로 전파하고 종료 시 정리한다. 외부 ID는 길이·문자·신뢰 경계를 검증하며 고유 ID나 인증 증거로 사용하지 않는다. 잠금과 로그인 실패처럼 한 요청의 여러 이벤트가 같은 request_id를 사용하게 한다. event_id는 각 사건별로 다르며 전송 재시도에서 유지한다. 비동기 작업은 명시적인 event_id/작업 ID를 전달하고 thread-local 로그 맥락이 자동 전파된다고 가정하지 않는다.

actor/target과 occurred_at은 관측 당시 서버가 확인한 값을 기록한다. 비동기 저장 시 현재 사용자 정보를 다시 조회해 과거 사실로 바꾸지 않는다. details는 이벤트별 허용 필드·길이·개수·전체 크기를 제한한다. 금지 키 검사만으로 모든 비밀값 유출을 막는다고 주장하지 않는다. 일반 파일 로그도 별도로 마스킹·입력 개행 처리·예외 내용 통제를 적용한다.

## 저장과 전달 순서

1. 감사 사실과 전달 대기를 동일 PostgreSQL 트랜잭션으로 저장한다.
2. backend의 전달 작업자 하나가 미전달 작업을 읽는다.
3. 네트워크 호출 동안 DB 트랜잭션을 유지하지 않고 내부 HTTP로 전송한다. 수신 포트는 외부에 공개하지 않으며 서비스 인증을 적용한다.
4. UBA가 event_id로 중복 제거하고 수신 이벤트와 분석 작업을 함께 커밋한 뒤 ACK한다.
5. backend가 전달 상태를 갱신한다. ACK 유실 시 동일 ID로 재전송한다. 같은 ID의 다른 내용은 계약 오류로 취급한다.

거부·실패 감사는 업무 롤백과 독립된 트랜잭션에 남긴다. 업무 변경과 감사가 함께 성공해야 하는 경우에는 같은 DB 트랜잭션에 참여한다. 저장 완료 후 전달을 분리하므로 UBA·Jev 장애가 원본 기록을 없애지 않는다.

원본 AuditHandler의 AFTER_COMMIT은 rollback 시 실행되지 않는다. fallbackExecution=true는 트랜잭션이 없는 경우의 실행일 뿐이다. 원본의 메모리 @Async 큐·저장 실패 로그는 내구성 보장이 아니므로 ZETTY 원본 감사의 유일한 저장 경로로 복사하지 않는다. CallerRunsPolicy의 호출 스레드 실행과 커밋 후 DB 쓰기 경계도 구분한다. 모든 오류를 공통 403 핸들러에서 자동 감사한다고 가정하지 않고 로그인/주문의 명시적 관측 지점을 정한다.

## 전달·분석 작업의 복구

초기에는 전달 작업자 하나를 사용하되 중복 스케줄 실행·재시작·처리 중 중단은 처음부터 다룬다. 짧은 트랜잭션으로 작업을 가져오고 네트워크 호출 뒤 별도 트랜잭션으로 상태를 갱신한다. DB 상태를 기준으로 복구하며 메모리 큐는 실행 보조 수단이다. 배치·실행기 큐 크기는 제한한다.

대기/처리 중/완료/재시도 대기/영구 실패의 실제 상태값, 시도 수, 다음 실행 시각, 시도 식별자와 timeout을 구현 계약에서 확정한다. 실행기 제출 실패 시 반납 또는 회수 절차를 두고 이전 시도의 늦은 완료가 새 시도·최종 상태를 덮어쓰지 않도록 조건부 갱신을 검증한다. 재시도 상한·backoff·운영 재처리 조건을 정한다. 다중 worker와 SKIP LOCKED/lease는 필요할 때 별도 설계하며 exactly-once라고 설명하지 않는다.

UBA의 Jev 호출도 SQL 트랜잭션 밖에서 수행한다. 호출 후 결과 저장 전 중단되면 외부 호출이 반복될 수 있음을 고려하고 보고서/분석 작업의 중복과 비용 한도를 검토한다. 수신 ACK, 분석 완료, 보고서 저장 완료는 서로 다른 상태다.

## 장애·권한·보관

일시 오류는 backoff 재시도하고 규격 오류는 별도로 보존한다. 미전달 수·가장 오래된 대기 시간·최종 오류를 관측한다. 전송 완료가 원본 감사 삭제 조건은 아니다.

앱 실행 계정에 감사 원본 UPDATE·DELETE 권한을 주지 않고, 전달 작업에는 필요한 조회와 전달 상태 갱신 권한을 부여한다. DDL·보관 삭제·백업용 권한은 구분한다. DB 관리자까지 변경 불가능한 저장소라는 주장은 하지 않는다.

파일 로그와 감사 DB의 보관 기간은 따로 정한다. 감사 DB 불가용 시 영속 기록을 보장할 수 없으므로 운영 오류를 기록하고 보호 응답 성공을 가장하지 않는다.

파일 로그는 지속 볼륨·비루트 쓰기 권한·회전 크기/총량·디스크 부족을 검증한다. 원본 dev/prod 파일 설정을 local에서도 자동 적용된다고 가정하지 않는다. 감사 조회는 기간/페이지 상한·필요 컬럼·시간+ID 커서를 사용하고 값은 SQL에 바인딩한다. FK와 제약은 관계별로 판단하며 원본의 전면적 FK 제거·월별 파티션을 기본값으로 복사하지 않는다. 보관 삭제는 별도 권한과 승인된 절차로 수행한다.

[모니터링 설계](monitoring-design.md)의 대기·실패·최종 성공과 unknown/유휴 구분을 적용한다. Health UP을 전달·분석 완료 증거로 사용하지 않는다.

## UBA 입력과 판정

로그인 이후 조회 순서·시간 차이·과거 이용 이력, 거부된 고유 주문 수·동일 대상 재시도·자기 주문 조회 전후 흐름을 구성한다. UBA 수신 시각을 별도 보관하고 지연·누락·이력 부족을 표시한다.

Jev 입력에는 관측 시점 이전 정보와 근거 event_id만 포함하고 실험 정답·시나리오 ID는 제외한다. 호출 실패·필수 기록 누락은 미평가, 유효한 관측으로 구분하기 어려운 경우는 근거 부족으로 남긴다.
