# L-07 Virtual Thread vs 플랫폼 스레드 (O-02)

- 상태: 완료(정직한 결론: 조건부·비확정)
- 연결: 로드맵 O-02 · Java 21 · COMPOSE.md §5(“VT를 켜도 DB 연결·CPU는 자동 제한되지 않는다”)
- 작성/갱신: 2026-09-27

## S — 문제
Java 21 Virtual Thread(VT)를 켜면 처리량이 오른다는 기대가 흔하다. 하지만 VT는 **I/O 대기가 길고 스레드 풀이 병목일 때** 이득이고, CPU 바운드나 다운스트림(DB 풀)이 병목이면 다르다. 실측으로 확인한다.

## T — 목표
같은 워크로드에서 플랫폼 스레드와 VT의 처리량·지연·오류를 비교하고, **어디서 이득이고 어디서 아닌지**를 수치로 말한다. 목표치를 미리 정하지 않는다.

## A — 어떻게
- `spring.threads.virtual.enabled`를 env(`VIRTUAL_THREADS`)로 토글. 워크로드는 `/mypage` 캐시 OFF(요청당 DB 조회 4회 = DB 바운드), 1500 RPS, hot.
- 변수: 스레드 모델(플랫폼 8 vs VT) × DB 풀(20 vs 100). 한 번에 하나씩.

## R — 결과 (1500 RPS, 45s, 단발)

| 설정 | 처리량 | p95 | 성공 |
|---|---|---|---|
| 플랫폼 8스레드 + 풀 20 | 1202 req/s | 6.9s | 87% |
| VT + 풀 20 | 790 | 19.5s | 77% |
| 플랫폼 8스레드 + 풀 100 | 530 | 35.8s | 77% |
| VT + 풀 100 | 810 | 19.7s | 80% |

### 해석 (정직하게)
- **VT는 공짜 성능이 아니다.** 풀 20에서 VT(790)가 플랫폼 8(1202)보다 **나빴다** — 수천 개 VT가 20개뿐인 DB 커넥션을 동시에 다투며 경합·큐잉이 커졌다. 플랫폼 8은 동시 진입을 8로 제한해 오히려 안정적이었다.
- 풀을 100으로 키우자(다운스트림이 병목이 아닐 때) VT(810)가 플랫폼 8(530)보다 **나았다** — 8스레드로는 큰 풀을 못 채우지만 VT는 채운다.
- 결론: **VT는 다운스트림 용량(DB 풀)에 맞춘 동시성 제한과 함께 써야 한다.** VT 자체가 풀 사이징·백프레셔를 대체하지 않는다(COMPOSE.md §5와 일치).

### 측정 한계 (반드시 함께 읽을 것)
- 1500 RPS는 이 호스트(12코어)에서 **부하 생성기·api·mysql이 CPU를 나눠 쓰는 포화 구간**이라 절대 수치의 노이즈가 크다(단발 측정). 표의 값은 "VT가 항상 낫다"를 반박하는 **방향성 근거**로만 쓰고, 정밀 처리량 벤치로 인용하지 않는다.
- 신뢰도 있는 확정에는 부하 생성기를 별도 호스트로 분리하고, 동시성 제한(세마포어) 버전을 추가해 3회 반복이 필요하다 → 후속.

## 자소서 한 줄
Java 21 Virtual Thread를 DB 바운드 경로에서 실측해 “무조건 이득”이 아님을 확인했습니다. 커넥션 풀이 병목이면 무제한 VT가 풀 경합으로 오히려 악화됐고, 풀을 키웠을 때만 VT가 유리해, VT는 다운스트림 용량에 맞춘 동시성 제한과 함께 써야 한다는 결론을 수치로 정리했습니다.
