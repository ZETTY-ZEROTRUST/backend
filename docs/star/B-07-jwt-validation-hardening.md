# B-07 v2:start — JWT 검증 강화(필수 claim·발급자·대상·토큰 종류·시각)

- 상태: 계획
- 연결: 로드맵 B0 → v2:start(SCENARIOS) · attack-simulation `scenarios/v2/start_jwt.py`(작성 예정)
- 작성/갱신: 2026-09-27

## S — 문제 (코드로 확인한 현재 동작)

`api-server/.../JwtVerifier.java`는 파싱 → RS256 고정 → kid·공개키 → 서명 → **exp가 있을 때만** 만료 확인이 전부다.

| 약점 | 영향 |
|---|---|
| `exp` 없으면 통과 | 만료 없는 토큰이 영구히 유효 |
| `iss`·`aud` 미검증 | 같은 키로 서명된 다른 용도·다른 대상의 토큰도 API가 받음 |
| `typ` 미검증 | Access Token이 아닌 JWT(예: ID 토큰)를 AT로 오인할 여지 |
| `nbf`·`iat`·최대 수명 미검증, 시계 오차 기준 없음 | 미래 발급·비정상적으로 긴 수명 토큰 허용 |
| JWKS 갱신이 `clear()` 후 `putAll()` | 그 사이 요청은 키를 못 찾아 정상 토큰이 401 |

지금은 **발급대장(S3)이 미발급 토큰을 막아서** 위 약점이 대부분 가려져 있다. 하지만 Auth 설정 실수 하나로 뚫린다: `JwtIssuer`는 `jwt.expiration <= 0`이면 `exp` 없이 발급하고, 그 토큰은 정상 발급이라 대장에도 기록되므로 **API가 영원히 받아들인다.** 방어가 한 겹뿐인 상태다.

## T — 목표

- 발급대장과 별개로 **검증기 자체가 필수 조건을 강제**한다(방어 심층화).
- 성공 기준(재공격)
  - alg none·HS256 알고리즘 혼동·변조·kid 없음·미등록 kid·깨진 형식 → 401
  - `exp` 없는 토큰(설정 실수로 발급된 것 포함) → 401
  - 만료(시계 오차 30초 초과) → 401
  - 발급자·대상·typ 불일치, 미래 발급(`iat`/`nbf`), 최대 수명(900초+오차) 초과 → 401
  - 정상 토큰은 200
- Auth는 `jwt.expiration <= 0`이면 **기동을 거부**한다(설정 실수를 발급 전에 차단).

## A — 어떻게 (계획)

- 검증기: `exp`·`iat`·`nbf`·`iss`·`aud`·`sub`·`jti` 필수. `iss`·`aud`는 설정값과 정확히 일치. 헤더 `typ=at+jwt`. 시계 오차 30초. `exp - iat <= 900 + 30`.
- 발급기: 헤더 `typ=at+jwt`, `exp`·`iat`·`nbf` 항상 기록, 만료 설정이 0 이하이면 기동 실패. 발급자·대상은 설정값으로.
- JWKS: 새 맵을 만든 뒤 참조를 한 번에 교체(원자적 교체)해 갱신 중 공백을 없앤다.
- 재공격 러너: 공격 토큰은 공개키로 만들 수 있는 것(alg none, HS256 혼동, 변조)과 **Auth 설정을 바꿔 실제로 발급받는 것**(만료 없음, 짧은 만료)으로 나눈다.

| 방식 | 판단 |
|---|---|
| Spring Resource Server(`NimbusJwtDecoder` + validator) | 표준 구현, 설정만으로 대부분 해결. 다만 현재 필터·사유 코드(C-02 이벤트) 구조를 크게 바꿔야 함 → 후속 전환 후보 |
