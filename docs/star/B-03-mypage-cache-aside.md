# B-03 /mypage: SQL 튜닝 → Cache-Aside(Redis) 단계 비교

- 상태: 진행(A·B 측정 중, C 코드 준비 완료)
- 연결: 부하 A/B/C 실험 · Redis 도입 체크리스트(SQL 튜닝 우선)
- 작성/갱신: 2026-09-27

## S — 문제

- `/mypage`는 요청 1건마다 DB 조회 4회(user·주소·최근 주문 5건·결제수단)를 순차로 수행하는 집계 조회다.
- 조회가 잦고, 수정은 드물며(프로필·주소 변경), 약간의 지연 반영을 허용할 수 있어 **캐시 후보**다.
- 다만 Redis부터 넣지 않고, **SQL 튜닝 → 캐시** 순서로 각 단계의 효과를 분리해 측정한다.

## T — 목표와 비교 조건

- 같은 부하에서 **A(기존 SQL) → B(SQL·인덱스 개선) → C(B + Cache-Aside·TTL)** 를 비교한다.
- 한 번에 하나만 바꾼다. 같은 이미지에서 설정/인덱스만 달리한다.
- 고정 조건: 데이터셋 동일(시드 500명 + heavy 주문 20만), 커넥션 풀 20, AT 900초, 컨테이너 자원 상한 동일.
- 부하: k6 `constant-arrival-rate`(일정 유입률, 반복당 요청 1건) → 설정 RPS = 요청 RPS. `dropped_iterations`로 실제 달성 여부 확인.
- 절차: **워밍업 30초(결과 버림) → 측정 60초 × 3회**.
- 요청 분포: hot(요청 80%가 상위 20% 사용자) / wide(무작위) / cold(빈 캐시 시작).
- 확인: p50·p95, 성공률, 달성 RPS, dropped, **캐시 적중률(API에서 직접 집계)**, DB 조회 감소, 정합성(수정 후 오래된 응답).

## A — 어떻게

### ① SQL 튜닝 (B)
- EXPLAIN으로 4개 쿼리를 점검: users(PK)·orders(`idx_orders_user_ordered`, L-2)·payments(user_id)는 인덱스를 탄다.
- **addresses만 `Using filesort`**: `ORDER BY is_default DESC, address_id`를 단일 `user_id` 인덱스가 덮지 못함.
- 개선: 복합 인덱스 `idx_addr_user_default (user_id, is_default DESC, address_id)` → filesort 제거 확인.
- 참고: InnoDB는 FK용 자동 인덱스(`user_id`)를 새 복합 인덱스가 대체하면 조용히 삭제한다(되돌릴 때 FK 제약으로 DROP 거부됨 → 단일 인덱스를 먼저 만들고 복합을 지움).

### ② Cache-Aside (C)
- 키 `mypage:{userId}`, 값 응답 JSON(Spring ObjectMapper). 적중 → 반환, 미스 → DB 로드 후 저장.
- **TTL + ±20% 지터**: 대량 동시 만료로 DB가 몰리는 스탬피드를 분산(L-04에서 TTL 동시 만료 스탬피드를 실측한 교훈).
- **쓰기 무효화**: `PUT /users/me`, `PUT /addresses/{id}` **커밋 성공 후(afterCommit)** 키 삭제. 롤백된 쓰기는 캐시를 지우지 않는다.
- Redis 장애 = 미스로 간주해 DB 폴백(요청 실패로 만들지 않음). 적중/미스/오류 카운터(`mypage_cache_requests_total{result}`)로 API 단위 적중률 집계.
- 플래그 `zetty.mypage-cache-enabled`(기본 false)로 A/B/C가 같은 이미지·설정만 다름.

### 설계상 주의 (정직하게 남기는 한계)
- **Write-Through/Around 원자성**: DB 커밋 후 캐시 삭제는 원자적이지 않다. 삭제 실패·경합(미스로 옛 값을 읽는 중에 쓰기 커밋→삭제→옛 값 저장) 시 **TTL이 불일치 상한**이 된다.
- **민감정보 캐시**: `/mypage`의 `defaultAddress`에 `doorPassword`(현관 비밀번호, 평문)가 포함된다. 캐시하면 민감정보가 Redis에 한 벌 더 생긴다. 현재 Redis는 내부망 전용(host 포트 없음)으로 완화했지만, 운영이라면 해당 필드를 캐시·응답에서 제외하거나 암호화하는 것이 맞다.
- Lettuce는 단일 연결을 공유하므로 "풀을 크게"가 기본 해법이 아니다(연결 설정은 측정된 병목이 있을 때 조정).

### 시행착오 — 불리한 조건 시험에서 발견한 버그
- TTL 1초로 낮은 적중률을 만들자 지터 계산이 0초를 낼 수 있었다. `SET EX 0`은 Redis 오류라 저장이 조용히 실패(DEBUG 로그만). → TTL 최소 1초 보장으로 수정.

### 시행착오 — 측정 방법 오류를 스스로 잡음
- 첫 A 측정(재배포 직후) p95 454ms, 이어서 B p95 3.2ms로 **140배 개선처럼 보였음**.
- 주소 1~2행의 filesort 제거로는 불가능한 차이 → 원인: **A는 JVM·커넥션 풀·MySQL 버퍼가 차가운 상태, B는 워밍된 상태**.
- 조치: 인덱스를 되돌려 A를 재현하고, 모든 측정에 워밍업 구간을 분리해 3회 반복으로 재측정.

## R — 결과

### 1. A(기존 SQL) 워밍업 후 재측정 — 200 RPS hot, 60초 × 3회

| 회차 | p50 | p95 | 성공률 | dropped |
|---|---|---|---|---|
| r1 | 2.3ms | 3.2ms | 100% | 0 |
| r2 | 2.4ms | 3.2ms | 100% | 0 |
| r3 | 2.4ms | 3.1ms | 100% | 0 |

- 앞선 "A p95 454ms"는 **콜드 스타트** 수치였다(재배포 직후 첫 실행). 워밍업 후 A = B(3.2ms).
- **결론 ①: addresses filesort 제거(SQL 튜닝)는 200 RPS에서 측정 가능한 효과가 없다.** 주소가 사용자당 1~2행이라 정렬 비용이 무시할 수준이다. 튜닝을 "했다"는 사실보다 "효과가 없음을 측정으로 확인했다"가 정확한 기록이다.
- **결론 ②: 200 RPS는 p95 3ms로 포화와 거리가 멀다.** 이 구간에서는 캐시 효과도 드러나지 않는다 → 단계 부하로 포화점(knee)을 먼저 찾는다.

### 2. A 단계 부하(knee 탐색) — hot, 워밍업 30초 후 30초 측정

| 목표 RPS | p50 | p95 | 성공률 | 달성 RPS | dropped |
|---|---|---|---|---|---|
| 400 | 1.8ms | 2.7ms | 100% | 400.0 | 0 |
| 800 | 2.0ms | 3.2ms | 100% | 800 | 0 |
| 1200 | 2.2ms | 13.7ms | 100% | 1200 | 0 |
| 1600 | 2.3ms | 180.7ms | 100% | 1600 | 0 |
| 2000 | 576ms | 2,747ms | **61%** | 1,215 | **336** |

→ 1600 부근이 포화 시작, 2000에서 붕괴. (2000 구간 DB 지표는 exporter 수집 지연으로 제외)

### 3. 같은 부하(1600 RPS, hot, 사용자 100명) A → B → C — 60초 × 3회

| 단계 | p50 | p95 | 성공률 | DB SELECT/s | 캐시 적중률 |
|---|---|---|---|---|---|
| A 기존 SQL | 2.2ms | 4.9~5.3ms | 100% | 8,004 | — |
| B 인덱스 추가 | 2.2ms | 5.3ms(r3) | 100% | 8,004 | — |
| C Cache-Aside(TTL 60s) | 1.6ms | 3.0~3.8ms | 100% | **1,613 (-80%)** | 99.8~99.9% |

- DB SELECT 8,004/s = 요청당 5회(마이페이지 4 + 인가 1)와 정확히 일치. C에서 남은 1,613/s는 **인가 확인(보안상 캐시하지 않음)** 이다.
- B 1회차는 재배포 직후 차가운 JVM에 곧바로 1600 RPS를 걸어 붕괴(p95 527초, dropped 33,907), 2·3회차에 A 수준으로 수렴 → 재배포 후 워밍업을 90초로 늘려 C를 측정.
- **이 조건은 캐시에 유리하다**: 사용자 100명·hot 80/20·TTL 60초면 키가 거의 항상 캐시에 있다. 불리한 조건은 아래 5절에서 별도 측정.

### 4. 처리 한계 — hot, 60초

| 목표 RPS | A | C |
|---|---|---|
| 2000 | p95 2,747ms, 성공 61%, dropped 336 | p95 21.5ms, 성공 100%, dropped 0 |
| 2400 | — | p95 132ms, 성공 100%, dropped 0 |

주의: A 2000은 30초 단발(워밍업 30초)이라 C와 조건이 다르다 → 같은 조건 재측정 예정.

부하 발생기(k6)가 같은 호스트(12 CPU)에서 돌아 서버와 CPU를 나눠 쓴다. 고부하 구간 수치에는 발생기 자원 경합이 섞일 수 있어 호스트 load average를 함께 기록한다.

### 5. 캐시에 불리한 조건 — 사용자 500명 무작위(wide), TTL 1초, 1600 RPS

미스 경로는 A보다 비싸다: A = DB 4회, C 미스 = Redis GET(미스) + DB 4회 + Redis SET.

| 시험 | 조건 | 결과 |
|---|---|---|
| C, 콜드 스타트 + 워밍업부터 1600 RPS | 재배포 직후 | **API OOM 강제 종료**(exit 137, 768MiB 초과), 성공 0%, dropped 약 88,000 |
| A 대조, 같은 조건 | 재배포 직후 | 생존. p95 21.1ms, 성공 100%, **메모리 710/768MiB(92%)** |
| C, 저속 워밍업(400 RPS) 후 1600 RPS | 정상 상태 | 생존. p95 5.0ms, 적중률 80.8%, DB SELECT 2,846/s(A 8,018 대비 -65%), 메모리 최대 714MiB |
| C, 동시 연결 상한 400 + 원래 콜드 조건 | 재배포 직후 | 생존. p95 4.5ms, 성공 100%, 메모리 최대 676MiB |

해석(정직하게):
- 정상 상태에서는 적중률이 81%로 떨어져도 DB 부하가 65% 줄고, 메모리는 A와 같았다 → **캐시가 메모리를 더 먹어서 죽은 것이 아니다.**
- 콜드 스타트에 최대 유입을 바로 걸었을 때 C만 죽고 A는 한도 직전(92%)으로 버텼다. 미스 경로가 느린 상태에서 개방형 부하(constant-arrival-rate)가 동시 요청을 늘린 것이 원인으로 보인다.
- 동시 연결 상한 400을 둔 재시험은 살아남았지만 **거절이 0건**이었다. 즉 상한이 실제로 작동하지 않았으므로 "상한이 OOM을 막았다"고 말할 수 없다. 첫 OOM이 재현되는지 상한 없이 다시 확인 중이다.
- 구조적 위험은 남는다: JVM이 컨테이너 메모리의 75%를 힙에 쓰도록 설정돼 있어 힙 밖(스레드 스택·Netty 다이렉트 버퍼)에 192MB밖에 없고, A도 92%까지 올라갔다.
