ZETTY · 서버 세션 backend 통합 설계안

2026-11-27 · PostgreSQL 선택 반영 · 구현 전

C1–C4 도면 7장 보기 · 설계안·원본·렌더링 다운로드

확정 방향: 서버 세션을 사용하는 backend 하나, 별도 uba-analyzer, PostgreSQL.
이번 산출물: 도면과 설계 설명. Java/Python 코드, Gradle, Docker, DB는 변경하지 않았다. 일반 프로젝트 문서는 이 설계 기준으로 교체했다.
세부 제안: 로컬 PostgreSQL 인스턴스 하나에 앱별 DB·계정을 분리하고 기존 Redis는 세션에 사용한다. 보고서 열람은 우선 로컬 CLI로 제안한다.

1. 목표와 시스템 경계

고객 로그인 이후의 계정 탈취 의심 행동과 반복 주문 접근을 관측한다. backend는 인증·인가를 집행하고 사실을 기록한다. UBA는 실험 종료를 기다리지 않고 계속 수신·집계·분석한다. Jev 응답을 기다리며 고객 요청을 막지 않는다.

브라우저 / 허가된 시나리오 실행
  → HTTPS Nginx → backend (Spring Boot JVM 하나)
                    ├─ Redis: 세션
                    ├─ PostgreSQL / zetty_backend: 사용자·주문·감사·전달 상태
                    ├─ 파일: 운영 로그
                    └─ HTTP 감사 전달 → uba-analyzer (Python 앱 하나)
                                           ├─ PostgreSQL / zetty_uba
                                           ├─ Jev HTTPS API
                                           └─ 저장된 초동보고서

두 논리 DB는 로컬 PostgreSQL 인스턴스 하나를 공유한다. DB·계정 분리는 접근 권한 경계이며, 물리 장애나 DB 관리자 권한까지 격리하지는 않는다. UBA는 backend의 업무 DB·Redis 접근 권한을 받지 않는다. 수신 포트는 외부에 공개하지 않고 backend용 서비스 인증을 적용한다.

내부 HTTP는 격리된 로컬 Docker 네트워크 가정이다. 외부 환경으로 배포할 때는 서비스 간 TLS와 비밀값 관리를 별도로 검토한다. 이 설계가 전체 제로트러스트 아키텍처를 구현했다는 뜻은 아니다. 인증·업무 통합으로 기존 프로세스 격리는 줄어든다.

2. trust-chain-server에서 가져올 구조

실제 settings.gradle.kts에는 domain, application, infrastructure, bootstrap-app 4개 모듈이 포함되어 있다. 이를 따른다. 실행 JAR와 backend 컨테이너는 각각 하나이고, 나머지 모듈은 코드 라이브러리다.

Controller는 HTTP 입출력, Facade는 인증 주체와 서비스 호출의 조합, Service는 업무 규칙을 맡는다. application이 infrastructure 구현체를 직접 참조하지 않는다. 원본의 테넌트·복잡한 RBAC·워크로드 JWT 기능은 이번 두 시나리오에 맞춰 가져오는 범위를 제한한다.

Java의 4계층 모듈 구조를 Python까지 기계적으로 복제하지 않는다. UBA의 HTTP 수신과 작업자는 한 앱에서 시작하되, 실행할 작업은 메모리 큐가 아니라 DB에 남긴다.

3. 로그인과 세션 흐름

  1. AuthController가 로그인 요청을 검증하고 AuthFacade에 전달한다. 로그인 시도 제한과 계정 사용 가능 상태를 확인한다.
  2. AuthenticationManager → SessionLoginAuthenticationProvider가 사용자와 비밀번호 해시를 조회하여 자격을 검증한다. 잘못된 비밀번호와 미존재 계정은 외부에 구분해 노출하지 않는다.
  3. 검증된 userId·권한·authVersion과 감사용 세션 식별자를 인증 주체에 담는다. 로그인 실패의 입력 ID를 검증된 사용자로 기록하지 않는다.
  4. SessionAuthenticationStrategy로 세션 고정을 방지하고 SecurityContextRepository로 인증 결과를 세션에 저장한다. Spring Session은 Redis에 세션을 보관한다.
  5. CSRF 토큰을 준비하고 로그인 결과를 감사 DB에 기록한다. 세션 저장·감사 저장 실패를 성공 로그인 응답으로 바꾸지 않는다.
  6. Secure·HttpOnly·SameSite 쿠키와 사용자 정보·CSRF 토큰을 응답한다. 브라우저용 AT/RT를 발급하지 않는다.

실제 세션 쿠키와 auditSessionKey는 별개다. 세션 ID가 교체되어도 필요한 감사 상관관계를 유지할 수 있도록 로그인 단위 식별자를 관리한다. 쿠키 원문을 로그나 UBA에 보내지 않는다.

후속 보호 요청은 세션을 복원한 뒤 DB의 현재 계정 상태·authVersion을 검사한다. 잠금·탈퇴·전체 로그아웃 등으로 버전이 달라지면 기존 세션도 거부한다. 유휴 만료와 절대 만료를 구분하고, 로그아웃은 세션 무효화와 쿠키 제거를 수행한다. Redis/DB 오류를 인증 성공으로 처리하지 않는다.

Redis와 PostgreSQL 사이에 원자적 커밋은 없다. 감사 실패 후 세션 정리, 세션의 실제 저장 시점, 응답 커밋 시점은 구현 때 통합 검증한다. 감사 기록의 성공이 브라우저 응답 수신이나 실제 사용자 신원까지 증명하지 않는다는 점도 구분한다.

4. 주문 인가 흐름

세션 복원 → 현재 계정 상태 확인
  → OrderController → OrderFacade
  → OrderService.getOwnedDetail(principal.userId, orderId)
  → OrderRepository.findByOrderIdAndUserId(orderId, userId)
     ├─ 조회됨: 감사 허용 기록 후 보호 응답
     └─ 조회 안 됨: 감사 거부 기록 후 동일한 404 응답

현재 OrderService의 주문 ID와 userId를 함께 제한하는 원칙을 유지한다. userId는 요청 파라미터가 아니라 서버가 인증한 principal에서 얻는다. 거부 사유는 OBJECT_NOT_FOUND_OR_NOT_OWNED로 기록하여 주문 부재와 타인 소유를 임의로 구분하지 않는다. 모든 404를 인가 거부로 분류하지 않는다.

업무 트랜잭션이 끝나거나 롤백된 뒤에도 거부 사실을 기록할 수 있도록 감사 저장 경계를 분리한다. 같은 클래스 내부 호출로 트랜잭션 어노테이션이 적용되지 않는 문제를 피하고, 별도 Spring 빈 경계를 사용한다. 감사 저장 실패 시 성공한 보호 응답 본문은 반환하지 않는 정책을 제안한다.

5. 일반 로그·감사 기록·전달

종류경로목적
일반 로그log.info/error → SLF4J → Logback → 마운트된 회전 파일앱 상태·DB 오류·전달 장애. 개인정보·비밀값을 기록하지 않음
감사 사실인증·인가 결과 → AuditService → audit_events발생 시각·주체·행위·대상·결과를 구조화
전달 상태동일 트랜잭션에서 audit_delivery 저장미전달·재시도·ACK 관리. 원본 감사 행과 구분

trust-chain-server는 AuditRecordEvent → AFTER_COMMIT AuditHandler → @Async AuditFacade → AuditService → DB 흐름이다. 메모리 비동기 구간과 저장 실패 시 오류 로그만 남기는 부분은 그대로 복사하지 않는다. 제티는 분석 근거의 유실을 줄이기 위해 DB에 먼저 저장하고 전송을 재시도한다.

감사 사실 + PENDING 전달 상태를 PostgreSQL에 함께 커밋
  → backend의 AuditDeliveryJob이 미전달 작업 조회
  → 같은 event_id로 UBA HTTP 전송
  → UBA가 이벤트 + 분석 작업을 자신의 DB에 함께 커밋
  → 저장 확인 ACK
  → backend 전달 상태를 ACKNOWLEDGED로 갱신

초기 전달 작업자는 1개다. 네트워크 호출 중 DB 트랜잭션을 잡아두지 않는다. UBA가 저장했지만 ACK가 유실되면 같은 event_id로 재전송한다. UBA는 이벤트와 분석 작업을 중복 생성하지 않는다. 같은 ID로 다른 내용이 오면 성공 처리하지 않고 계약 오류로 기록한다.

일시 장애는 backoff 재시도, 잘못된 스키마·서비스 인증 실패 등은 오류 원인을 보존하고 운영자가 확인한다. 미전달 건수와 가장 오래된 대기 시간을 관측한다. 전송 완료 후에도 audit_events 원본은 보관 정책에 따라 유지한다.

업무 변경과 감사가 함께 성공해야 하는 기능은 같은 PostgreSQL 트랜잭션에 참여시킨다. 거부·실패는 롤백되는 업무와 분리한 감사 트랜잭션을 사용한다. DB 자체가 불가용하면 영속 감사 기록도 보장할 수 없으므로 운영 오류를 남기고 성공을 가장하지 않는다.

6. PostgreSQL을 선택한 이유와 데이터 형태

공통 필드는 관계형 컬럼으로 제약·검색하고, 이벤트별 추가 맥락은 JSONB로 저장한다. JSONB는 필요한 포함 조건·키 검색에 GIN 인덱스를 사용할 수 있어 조사 조건의 확장에 유리하다. 현재 두 시나리오의 기본 집계만으로 MySQL보다 빠르다고 주장하지는 않는다. PostgreSQL JSONB 공식 문서

저장 위치테이블·필드 제안설명
zetty_backendusers, orders, order_items, addresses, payments 등기존 업무 기능을 옮김. PostgreSQL 선택만으로 업무 기능을 삭제하지 않음
zetty_backend.audit_eventsevent_id UUID, schema_version, occurred_at TIMESTAMPTZ, actor_key, audit_session_key, request_id, event_type, action, resource_key, outcome, reason, details JSONB고유 ID·필수 값·허용 결과에 제약 적용. 원시 개인정보와 인증 자격 제외
zetty_backend.audit_deliveryevent_id, status, attempts, next_attempt_at, acknowledged_at, last_error_code감사 사실과 분리한 변경 가능한 전달 상태
zetty_ubareceived_events, analysis_jobs, reportsevent_id 중복 방지, received_at 별도 보관, 분석 종료 시각·버전·증거 참조 관리

처음에는 event_id 고유 인덱스, 사용자/세션과 발생 시각의 조회 인덱스, 미전달 작업 조회 인덱스부터 설계한다. GIN은 실제 JSON 검색 조건이 생기면 검토하고, 파티셔닝은 데이터 규모와 보관 작업이 요구할 때 추가한다. JSONB는 원래 JSON의 공백·키 순서까지 보존하는 원문 보관 형식이 아니다.

앱 실행 계정과 마이그레이션 계정을 구분한다. 감사 원본은 실행 계정에 필요한 INSERT·조회 권한만 주고 UPDATE·DELETE를 제한한다. 전달 작업은 원본 조회와 전달 상태 갱신만 가능하도록 설계한다. UBA 계정에는 backend DB 권한을 주지 않는다. DB 소유자·관리자는 여전히 강한 권한을 가지므로 이 설계만으로 변조 불가능한 저장소가 되지는 않는다.

보관 기간·백업·삭제 작업은 일반 파일 로그와 감사 기록별로 정한다. 참조 프로젝트의 파일 보관 일수를 법적 감사 보존 기간으로 그대로 사용하지 않는다.

7. 두 시나리오에 필요한 관측과 UBA 처리

시나리오입력 기록비교할 정상 설명
로그인 이후 계정 탈취 의심로그인 성공, 같은 감사 세션의 조회 순서·시간 차이, 접근 종류, 과거 계정 이용 이력본인의 배송지 확인, 새 환경에서의 정상 이용. 관측이 같으면 실제 사용자 여부를 단정할 수 없음
반복 주문 접근허용·거부, 가명 대상별 고유 수, 동일 대상 재시도, 첫 거부 이후 행동, 자기 주문 조회 전후 흐름계정 전환 후 오래된 탭 재접근. 거부된 주문이 실제 타인 소유였다고 단정하지 않음

HTTP 수신은 DB 저장까지만 완료하고 ACK한다. 작업자가 저장된 작업을 계속 읽어 짧은 관측 구간과 비교 가능한 과거 이력을 구성한다. 예를 들어 전송은 수초 간격, 분석은 수십 초 구간으로 시작할 수 있지만 이 값은 실측 전 가정이며 확정 SLA가 아니다.

occurred_at과 received_at을 구분하고, 늦게 온 이벤트·관측 누락·이력 부족을 입력에 표시한다. 보고서에는 분석에 사용한 종료 시각, 근거 event_id, 집계 버전과 보고서 버전을 보관한다. 사후 정답·시나리오 ID는 Jev 입력에 넣지 않는다.

Jev의 선택값과 지원되는 판정 정보를 검증해 관측 사실과 결합한다. 근거 참조·영향 범위·미확인 사항을 포함한 보고서는 UBA가 README의 내부 양식에 맞춰 구성한다. 자유 형식 보고서 생성이 Jev에서 제공된다고 가정하지 않으며 실제 API 계약은 구현 전에 확인한다.

Jev 호출 실패나 필수 이벤트 누락은 미평가, 유효한 관측만으로 설명을 구분하기 어려운 경우는 근거 부족이다. 조회 성공, 개인정보 반환 확인, 외부 반출 확인은 서로 다른 사실이다. AI 결과만으로 계정을 자동 차단하지 않는다.

UBA README는 두 시나리오와 PostgreSQL 수신·분석·보고서 흐름으로 정리했다. 현재 도면의 열람 경로는 로컬 CLI 제안이며 Slack 전달·담당자 인수 자동화는 최소 구현 범위에 포함하지 않았다.

8. 현재 코드에서 옮길 것과 제거 후보

현재목표
auth-server: 계정·비밀번호 검증identity 서비스 + 세션 로그인 Provider로 이동
api-server: 업무 API·주문 소유권 검사해당 업무 모듈과 Facade로 이동
bff-server: 쿠키·세션·CSRF·Originbootstrap-app 보안 설정으로 통합
BFF의 Auth/API HTTP 중계같은 JVM 내 서비스 호출
AT/RT·JWT 서명·JWKS·발급대장·토큰 보관함·회전 조율브라우저 서버 세션 범위에서 제거 후보. 새 인증 검증 후 정리
JWT 서명 전용 KMS 연동다른 사용처가 없는지 확인 후 제거 후보
MySQL 드라이버·DDL·SQL·테스트·Compose향후 승인된 PostgreSQL 전환 단계에서 변경. 이번에는 변경 없음

전환 시 AUTO_INCREMENT/identity, 시간 타입, JSON 매핑, 예약어, upsert, 대소문자·문자열 비교, 네이티브 SQL, 시퀀스와 테스트 데이터를 점검한다. 운영 DB를 덮어쓰지 않고 별도 PostgreSQL 환경에서 검증한다. 기존 데이터의 보존·이관·폐기 방식은 실제 DB 변경 전에 별도로 정한다.

9. 함께 구현하고 확인할 순서

  1. 구조: 4개 Gradle 모듈과 실행 앱 1개를 만든 뒤 의존 관계와 bootJar를 확인한다.
  2. PostgreSQL: 별도 로컬 DB와 계정을 준비하고 사용자 조회·비밀번호 해시 읽기부터 확인한다. 기존 MySQL 데이터는 이 단계에서 자동 삭제하지 않는다.
  3. 세션 로그인: Docker HTTP 요청의 Set-Cookie, Redis 세션, 다음 요청의 인증 복원을 함께 본다. CSRF·만료·로그아웃·계정 상태 변경도 확인한다.
  4. 주문 인가: 본인 주문 성공과 타인/미존재 주문 거부를 재현하고, 요청 userId 조작이 무시되는지 확인한다.
  5. 로그·감사: 일반 파일 로그와 PostgreSQL 행을 나란히 보고 request_id로 연결한다. 롤백·감사 저장 실패 시나리오를 확인한다.
  6. UBA 전달: 수신 중단·재시작·ACK 유실·중복 전송·잘못된 이벤트를 시험한다. DB 저장 후 ACK와 중복 작업 방지를 확인한다.
  7. AI·보고서: 합성 공격/정상 대조군으로 관측·Jev 입력·결과·보고서 근거를 확인하고 API 실패도 미평가로 남는지 본다.

각 단계는 변경 파일·이유·실제 요청 흐름을 먼저 설명하고 승인받은 범위만 구현한다. 이 문서의 검증 항목은 앞으로 수행할 계획이며 실행 결과가 아니다.
