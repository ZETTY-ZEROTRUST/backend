# 실시간 통신 방식 적용 판단 (SSE · Webhook · Polling · WebSocket)

- 상태: 설계 판단(미구현). 적용 시 각 항목은 STAR 문서로 착수한다.
- 작성: 2026-09-27

## 판단 기준

1. **방향**: 서버→클라이언트 단방향인가, 양방향인가.
2. **보안 경계**: 장수 연결이 "매 요청 회수 확인"(S2) 원칙을 우회하지 않는가.
3. **전달 보장**: 유실·중복·순서가 문제인가(멱등성·재시도 필요 여부).
4. **부하 특성**: 연결을 오래 잡는가(스레드·메모리), 주기 조회 비용이 큰가.

## 적용 후보

| 방식 | 적용 위치 | 판단 | 근거 |
|---|---|---|---|
| **SSE** | 세션 회수 즉시 알림: S2 전체 로그아웃, S4 대응(REQUIRE_REAUTH·REVOKE_SESSION) 시 BFF가 브라우저에 이벤트 전송 → 화면 로그아웃·재인증 유도 | **적합(1순위)** | 서버→클라이언트 단방향이면 충분. HTTP 위에서 동작해 BFF 세션 쿠키·CSRF 경계를 그대로 사용. 연결마다 스레드를 점유하므로 Virtual Thread 비교(L-7)의 부하 대상으로 좋다 |
| **SSE** | 관리자 탐지 대시보드 실시간 피드(anomaly-detection 결과) | 적합 | 읽기 전용 단방향 |
| **Polling** | Outbox relay가 MySQL 미전달 이벤트를 lease로 주기 조회(계약 문서의 기본 설계) | **이미 계획** | 단순·원본(MySQL) 중심 복구가 쉬움. 대안 CDC(Debezium)는 지연↓·운영 복잡도↑ → 트레이드오프를 부하로 비교(L-6) |
| **Polling** | UBA 탐지 주기 실행(윈도우 단위) | 유지 | 윈도우 집계 특성상 주기 실행이 자연스러움 |
| **Webhook** | UBA 정책(Codex)이 만든 ResponseCommand를 Auth/BFF 집행기로 전달 | **조건부** | 서명(HMAC)·`command_id` 멱등·만료·재시도·수신 확인이 필수. 계약 문서 기본안은 Redis Streams(재처리·pending 회수 용이) → webhook vs stream을 비교해 결정 |
| **Webhook** | Slack 등 외부 알림 | 보류 | AGENTS.md: 외부 발송을 자동으로 시작하지 않는다 |
| **WebSocket** | — | **비권장** | 양방향 요구 없음. 한 번 인증한 장수 연결은 요청마다 하던 authVersion·발급대장 확인을 우회한다. 쓴다면 회수 시 서버가 연결을 강제 종료하고 주기적으로 상태를 재확인해야 한다 |

## 보안 주의 (공통)

- 장수 연결(SSE 포함)은 연결 시점 인증만으로 끝내지 않는다. 회수 이벤트(authVersion 증가·세션 폐기) 시 해당 사용자의 연결을 서버가 닫는다.
- 이벤트 본문에 토큰·세션 ID·민감정보를 넣지 않는다. "재인증 필요" 같은 신호만 보낸다.
- Webhook 수신 측은 서명·타임스탬프 검증으로 위조·재전송을 막고, 같은 `command_id`는 한 번만 집행한다.

## 적용 순서(제안)

1. **SSE 회수 알림** — BFF 도입(A-03) 이후. S2 재공격 시나리오에 "회수 후 브라우저가 몇 초 안에 로그아웃되는가"를 지표로 추가.
2. **Outbox polling** — 이벤트 파이프라인(Phase 6). 폴링 주기·배치 크기별 전달 지연과 DB 부하 측정.
3. **ResponseCommand 전달** — S4 대응 단계(Phase 7). webhook과 Redis Streams를 같은 장애 시나리오(수신 측 중단·중복 전송)로 비교.
