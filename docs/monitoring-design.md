# 상태 확인과 감사 전달·분석 모니터링 설계

선택한 목표 설계이며 아직 구현된 endpoint·메트릭·대시보드가 아니다. 기존 C4의 단일 backend·UBA·저장소 경계를 유지한다. 새 서버나 Prometheus/Grafana/APM을 필수 구성으로 추가하지 않는다.

## 원본에서 참고할 부분

trust-chain-server는 Actuator `health,info`만 HTTP 노출하며 probes를 켠다. 외부 DB는 root health에서 제외하고 addons 그룹에서 관측한다. 다만 활성화된 외부 DB에 기동 시 접속할 수 없으면 기동을 실패시킨다. 이는 원본의 선택이며 ZETTY의 정책은 아래와 같다.

원본은 공개 health 경로에서 `show-details: never`를 사용하나 addons의 구성 요소 상태는 표시한다. 작업 watchdog은 중단 작업을 회수하는 코드이고 외부 알림 플랫폼은 아니다. 사용자 정의 MeterRegistry 계측·Prometheus 수집·Grafana 대시보드·APM 연동은 조사한 원본에서 확인되지 않았다. Actuator 의존성만으로 이 기능들이 구현됐다고 보고하지 않는다.

## 장애를 구분하는 기준

| 대상 | 목표 판정과 대응 |
|---|---|
| backend liveness | 프로세스 자체의 생존성. UBA/Jev/외부 네트워크 장애를 이유로 backend 재시작을 유도하지 않는다. |
| backend readiness | 요청을 안전하게 처리할 필수 PostgreSQL·Redis와 앱 준비 상태. 상태 검사에 명시적으로 포함하고 장애 시 보호 요청을 허용하지 않는다. |
| UBA 수신 readiness | 서비스 인증 설정과 UBA DB의 저장 가능 상태. Jev 중단 중에도 이벤트+작업을 저장할 수 있으면 수신은 계속한다. |
| UBA 분석 상태 | 작업자 진행 여부·대기·Jev 실패를 수신 readiness와 별도로 관측한다. 프로세스 UP만으로 분석 정상이라고 보고하지 않는다. |
| 전달/분석 지연 | backend 업무는 계속될 수 있어도 보안 관측이 지연되는 상태다. 운영자가 대기/실패를 확인하고 복구 후 전달·분석 재개를 검증한다. |

초기화 시 필수 저장소·필수 설정이 없으면 ready로 보고하지 않는다. 세부 기동 재시도 정책은 구현 단계에서 정한다. backend 시작을 UBA/Jev 접속 성공에 묶거나, UBA 시작을 Jev의 즉시 응답에 묶지 않는다. 필수 DB 장애와 외부 분석 의존성 장애의 경계를 테스트한다.

## 최소 관측값과 소유자

| 소유자 | 관측값 | 해석 |
|---|---|---|
| backend | 감사 저장 실패 수·최근 실패 시각 | 기록 누락 가능성. DB 자체가 죽으면 같은 DB에 실패 지표를 저장할 수 없으므로 파일 오류도 남긴다. |
| backend delivery | 대기 건수, 가장 오래된 대기 경과 초, 재시도 건수, 영구 실패 건수 | UBA 중단·인증 오류·계약 충돌을 구분한다. |
| backend delivery | 최종 수신 확인 시각, 전송 소요 시간, 마지막 오류 코드 | 전송 ACK는 분석 성공이 아니다. |
| UBA receiver | 수신 성공·중복·내용 충돌·인증/규격 거부 건수 | 중복 성공을 새로운 분석 작업으로 세지 않는다. |
| UBA jobs | 대기·처리 중·실패·복구 건수, 최장 대기, 최종 진행/완료 시각 | 중단과 유휴를 구분한다. |
| UBA Jev/report | 호출 소요 시간·실패/규격 위반, 보고서 저장 실패, 마지막 성공 시각 | 미평가·근거 부족·정상 판정을 분리한다. |

관측 시각·단위·집계 기간·재시작 시 카운터 초기화 여부를 표시한다. 대기 없음의 나이는 0, 한 번도 성공하지 않은 시각은 null/없음, DB 조회 불가는 unknown으로 구분한다. 프로세스 로컬 누적 카운터를 영속 감사 건수로 설명하지 않는다. event_id/request_id/actor/IP/전체 URL을 메트릭 label로 사용하지 않는다. 제한된 outcome·오류 종류 등 낮은 cardinality 차원만 쓴다.

초기에는 내부 운영 조회/CLI와 회전 파일로 확인하는 안이다. 실제 노출 방법·endpoint 이름·계측 라이브러리·임계값은 해당 구현 단계에서 정하며 없는 명령을 실행 지침으로 쓰지 않는다. 통합 메트릭 플랫폼, 자동 재시작/차단, Slack 알림은 최소 범위 밖이다.

## 로그와 공개 범위

- 일반 파일 로그는 request_id로 감사 기록과 연결한다. worker 로그는 event_id/작업 ID/시도 식별자와 안정적인 오류 코드로 추적한다. 이 값은 인증 자격이 아니다.
- 비밀번호·Bearer·세션 쿠키·CSRF·원문 개인정보·query/body를 기록하지 않는다. 예외 스택도 드라이버/HTTP 오류에 비밀값이 섞이는지 확인한다. 감사 필드 검사만으로 일반 로그 마스킹을 보장하지 않는다.
- 파일 회전 크기·총량·보존 기간, 볼륨·쓰기 권한·디스크 부족 시 동작을 별도로 정한다. 원본의 100MB/7/3GB 값을 보안 규정이나 ZETTY 확정값으로 가져오지 않는다.
- 공개 health는 최소 상태만 보여주고 JDBC 오류·내부 주소·토폴로지·스택을 숨긴다. 운영 상세·메트릭·작업 목록은 내부 접근과 별도 운영 권한으로 제한한다. UBA 수신 자격증명을 운영 조회 권한으로 재사용하지 않는다.
- management 경로·포트·프록시 허용 범위는 함께 검토한다. 보호 endpoint에서는 기능·객체 인가를 유지한다. health의 UP 응답은 전체 제로트러스트 구현이나 공격 탐지 성공의 증거가 아니다.

## 인수 기준과 담당

1. Java 담당: 실제 Health의 PostgreSQL·Redis 포함 여부와 공개 응답을 검증한다. 기본 probe 활성화만으로 필수 저장소 readiness가 보장된다고 가정하지 않는다.
2. Java/Python 담당: UBA 중단 시 backend 전달 대기·나이가 증가하고, 재개 시 동일 ID 재전송과 멱등 수신으로 해소되는지 확인한다.
3. Python 담당: Jev 중단 중 수신 ACK는 저장 뒤 성공하고 분석 실패/미평가가 별도로 보이는지 확인한다. 재시도한 이전 시도의 늦은 결과가 최신 작업을 덮어쓰지 않게 한다.
4. tester: 필수 DB·Redis 장애, ACK 유실, worker 중단/재시작, 중복/충돌, 유휴/관측 불가를 구분하는 검증을 담당한다. 실행되지 않은 장애 실험은 PASS가 아니다.
5. devops: 승인된 실행 단계에서 내부 포트, TLS, 로그/DB 볼륨·권한·회전·종료 시 동작을 검증한다. 문서 작업만으로 컨테이너/공격/유료 호출을 실행하지 않는다.
